  - Rationale: Lead sourcing mechanism was unclear (running Google Ads yourself is capital-heavy and slow; "improving contractor intake" felt like a support service, not a core business). Did not have a clear operational wedge before discovery. Applied "feasibility first, validation second" principle and determined the feasibility story wasn't compelling.
  - Next action: Return to whiteboard. Brainstorm alternative niches/ideas.

- Decision: Explore real estate MLS listing automation as candidate niche.
  - Rationale: Friend reports real pain (manual MLS data entry is slow/tedious). Real estate agents have money and clear workflows. Market signal is strong (Rechat, Cotality, Writor all exist, proving pain is real). Existing solutions might have gaps (price, simplicity, focus). Feasibility to validate: can we auto-fill MLS forms or generate listing descriptions? Operationally simpler than lead-gen (no customer acquisition problem, just agent workflows).
  - Next action: Run discovery call with friend this week. Understand exact pain point, WTP, and competitive gaps. Then decide on v1 service/product wedge (voice dictation, description generation, form auto-fill, or manual service).
  - Doc: [02-ideas/real-estate-mls-app.md](../04-planning/mls-app/real-estate-mls-app.md)
  - Tracking: [02-ideas/candidates.md](../02-ideas/candidates.md)

- Decision: Product hypothesis for MLS automation is "unified input + MLS auto-fill via browser extension (Michigan/FlexMLS only)"
  - Rationale: Competitors specialize in one input type (Writor=text, Restb.ai=photos, Cotality=app). No one offers flexible input (dictation + photos + documents) with direct MLS integration. Pricing undercut ($30-50/mo vs Rechat's $100-300/mo) is viable for solo agents. Michigan-only scope reduces complexity (one MLS system, not 100+). Blake has high conviction: "I KNOW realtors would use this."
  - Hard constraints: Build SOFTWARE (not service). Build in 4-6 weeks. Michigan only.
  - Feasibility: Chrome extension DOM injection is known-good (2-3 weeks). AI consolidation is known-good (2-3 weeks). UNKNOWN: Does Spark API support listing creation? (determines clean integration vs. fragile DOM manipulation).
  - Next action: Research Spark API write capability (email api-support@sparkplatform.com). Then run friend discovery call to validate/quantify demand.

- Decision: EXPAND product hypothesis from "MLS auto-fill" to "vendor scheduling + MLS auto-fill + payment integration."
  - Rationale: Blake's direct observation (does drone photography for realtor, sees admin's workflow) reveals TWO pain points: (1) manual listing data entry (paramount), (2) vendor scheduling (significant). Current market is fragmented: photo scheduling tools (Tonomo, HDPhotoHub, Aryeo) exist separately from MLS tools (Rechat, Cotality, Writor). Nobody integrates vendor scheduling + MLS posting + payment. This is the wedge.
  - Customer shifts from "solo agents" to "office admins" (who actually do all the work)
  - V1 Product: Unified system — schedule photo shoot → receive photos → auto-fill MLS → track/pay invoices (all in one platform)
  - Next action: (1) Confirm Spark API write capability, (2) Research payment integration feasibility, (3) Deep competitive check to verify no one is solving vendor scheduling + MLS integration, (4) Admin interview (Blake's contact) to validate full workflow pain.
  - Doc: [real-estate-office-workflow-expansion.md](../04-planning/mls-app/real-estate-office-workflow-expansion.md)

- Decision: Competition research is equally important as feasibility + validation.
  - Rationale: A great idea with heavy incumbent competition = struggle. Before validating demand, confirm competitive gap exists. In this case: vendor scheduling tools exist, MLS tools exist, but nobody integrates both. If someone is already building this, product is less defensible.
  - Next action: Systematic competitive research on all tools in vendor scheduling + MLS space before committing to build.
  - Applies to all future business ideas: feasibility + validation + competition analysis (all three required).

- Decision: Legality is non-negotiable and equally critical as feasibility, validation, competition.
  - Rationale: Landtrack taught us that legally gray areas are fatal to businesses. Before we validate demand or commit to build, we must confirm the idea is legally sound. For the real estate workflow tool, four critical legal questions must be answered: (1) Data privacy compliance, (2) MLS ToS/licensing, (3) Real estate licensing, (4) Fair Housing Act compliance.
  - Next action: Research FlexMLS ToS before Spark API research. Get Michigan real estate attorney opinion on licensing. Get data privacy review before building. Confirm all four legal questions have clear "yes" answers before proceeding.
  - Doc: [legal-risk-assessment.md](../04-planning/mls-app/legal-risk-assessment.md)
  - Applies to all future business ideas: feasibility + validation + competition + legality (all four required).

- Decision: FlexMLS ToS research complete — 3rd-party integrations are CLEARED.
  - Findings: FlexMLS explicitly permits 3rd-party integrations. They have 70+ integrations available via Spark Store. No special approval needed to build/offer tool. Data sharing and credential restrictions are non-issues for this product design.
  - Remaining legal question: Does Spark API support listing creation via POST/PUT? (Not a ToS risk; determines architecture. Awaiting api-support@sparkplatform.com response.)
  - Doc: [flexmls-tos-research.md](../04-planning/mls-app/flexmls-tos-research.md)
  - Docs updated: [legal-risk-assessment.md](../04-planning/mls-app/legal-risk-assessment.md), [candidates.md](../02-ideas/candidates.md)

- Decision: Pivot to modular product design with dual customer segments.
  - Rationale: Product serves two distinct customer groups with different pain points. Solo agents want just auto-fill + AI descriptions. Office admins want full workflow (scheduling + auto-fill + payment). Building one core product (auto-fill + AI) that serves both, with optional vendor scheduling layer for offices, is simpler to validate and scales better.
  - V1 Launch Strategy: Build core → validate with solo agent (easier, faster) → expand to offices (higher LTV)
  - MVP Scope: Weeks 1-3 core product. Weeks 4-5 vendor layer. Week 6 polish.
  - Pricing strategy: $30-50/mo solo agents. $100-200+/mo offices (with optional vendor scheduling).
  - Doc: [real-estate-office-workflow-expansion.md](../04-planning/mls-app/real-estate-office-workflow-expansion.md), [system-architecture-sketch.md](../04-planning/mls-app/system-architecture-sketch.md)
